# Herdr-native OMP orchestrator — first slice

Date: 2026-09-25
Status: design approved in conversation; implementation not started

## Goal and boundary

Make parallel work feel like talking to one agent rather than managing terminal tabs. In one Git repository, a primary Oh My Pi (OMP) session breaks independent coding requests into worker tasks, delegates them automatically, watches for questions and results, and brings decisions back to the user. A terminal Kanban board provides an overview and a way to inspect a worker without becoming another inbox.

This is a **new standalone Herdr plugin repository**, alongside the AO reference checkout. It is not a fork or modification of AO. Windows is the first supported platform; portable Herdr CLI boundaries should make later macOS/Linux support possible without promising it in this release.

A successful first run is: launch a primary in a project, ask for two independent changes, observe two isolated OMP workers and their cards, answer a worker blocker through the primary, inspect the two resulting branches, detach and reconnect, and find the same work and board state. No desktop or browser UI is involved.

## Scope

In scope: one local Git repository, one primary OMP session, up to three concurrent OMP workers by default, Herdr-managed worktree workspaces, structured task records and worker reports, primary-led blocker handling, a keyboard-driven board with status and drill-down, startup reconciliation, and explicit user-controlled integration and cleanup.

Out of scope: multi-repository fleet, other agent harnesses, remote workers, GitHub PR/CI/review automation, automatic merge, agent-to-agent hierarchy, mobile access, a standalone network daemon, and reproducing AO's Electron/Go/SQLite-CDC architecture. AO is an idea source for isolated workers and the separation of durable facts from display status, not code to transplant.

## Ownership and interfaces

- **Herdr** owns persistent terminal processes, layout, worktree checkout/workspace creation, focus, and OMP agent lifecycle/session restore. Require a Herdr version supporting plugin panes/events, native worktrees, and OMP integration (target the documented 0.9.1 surface; verify exact minimum during planning). Install and verify `herdr integration install omp` separately. The plugin never reports a competing OMP lifecycle authority.
- **Plugin core** is a single Go executable (`herdr-omp-orchestrator.exe` on Windows) for actions, event/startup hooks, coordinator CLI, SQLite persistence, and the terminal board. No Bash, Python, Node, or Bun runtime is needed on the plugin side. A build from source requires Go; a Windows release should package the compiled executable with the manifest. It owns project binding, task transitions, dispatch/reconciliation, an inbox of worker events for the primary, and the board read model. Its data lives in `HERDR_PLUGIN_STATE_DIR`, not in the project checkout or installed plugin source. SQLite transactions protect concurrent actions/hooks. The project key is the canonical repository root; first release binds one root per primary.
- **OMP extension** is a separate TypeScript file using OMP's `registerTool` API. Primary tools dispatch, inspect tasks/inbox, relay a specifically authorized answer, and record review disposition; worker tools report progress, blockers, and final results. Each tool spawns the Go executable with a fixed subcommand, sends versioned, size-bounded JSON on stdin, and parses a size-bounded JSON success/error response on stdout. The executable requires inherited `HERDR_ENV`, checks the caller's OMP session identity, and resolves role/task from the live process's launch-time `HERDR_PANE_ID` and persisted binding. If Herdr restores the same OMP session with a changed launch ID, a bounded verified rebind by OMP session, terminal and worktree provenance must happen before any tool becomes active; it uses a separately tracked current public pane ID for Herdr CLI operations. A worker cannot mutate another task through these tools. No shell command interpolation is involved. This is a trusted local-user boundary, not a sandbox against a malicious process running as that user.

The plugin's explicit setup action installs its own uniquely named extension in OMP's effective user extensions directory, alongside but never over Herdr's `herdr-omp-agent-state.ts`. It resolves the effective directory using OMP's active-profile rules (`OMP_PROFILE`/`PI_PROFILE`, then `PI_CODING_AGENT_DIR` for the default profile and `PI_CONFIG_DIR`), verifies Herdr's OMP integration is installed, and requires user approval before changing OMP files. Setup embeds the plugin executable's absolute path and bridge protocol version in the generated extension; reinstall/update refreshes that binding and a stale/missing executable fails visibly. On ordinary OMP launch and `omp --resume=<session>`, OMP discovers the same extension. Register role tools inactive at load, then activate only the verified primary/worker tool set after session-start binding/reconciliation; unrelated OMP panes remain unaffected. A restored process with an unrecognized new launch ID must not permanently lose its tools merely because plugin startup reconciliation runs after agent restore; retry a bounded session-identity rebind before its next user turn and surface failure as attention rather than silently disabling the extension. Do **not** pass an additional `--extension` flag: relying on launch argv would lose tools on Herdr's bare resume, while both paths risk duplicate registration. If discovery is disabled or extension loading fails, fail setup/recovery visibly rather than running workers without tools.
- **Board pane** is a Herdr plugin terminal pane with a keybinding/action to open it. It reads task state but has no direct dispatch, reassignment, approval, merge, or destructive cleanup commands. Selecting a card shows the brief, branch, report and last observation; another key focuses the recorded worker pane. The board does not identify work by a mutable label.

The core interfaces are `TaskStore` (atomic task/inbox updates), `HerdrClient` (typed wrappers around returned CLI JSON, invoked through the Herdr executable path supplied as `HERDR_BIN_PATH` to plugin commands on Windows), `TaskCoordinator` (validated transitions and orchestration), and `BoardView` (read-only projection). Setup carries that verified executable path into the OMP extension's bridge environment; do not assume an arbitrary Herdr-managed agent pane inherits plugin-only environment variables. The TypeScript extension invokes only versioned `Bridge` subcommands of the Go executable; the bridge validates pane/session binding, returns a structured error on version mismatch, and never lets extension code open SQLite or Herdr's Windows named pipe directly. Herdr's plugin startup/event hooks invoke the same executable. The extension uses OMP's runtime only; the plugin core does not need a JavaScript runtime or a long-lived coordinator service.

## Launch and dispatch

1. A plugin action binds an explicit Git repository and starts a dedicated primary OMP in its Herdr workspace, or reopens the previously recorded primary if it is still the same agent. It verifies OMP extension discovery and Herdr integration readiness first, then records exact session/workspace/pane identities from Herdr responses. A new primary is not silently substituted for a missing one.
2. The user talks to the primary. It may plan normally, but it automatically delegates independent, bounded tasks up to the concurrency limit; dependent tasks remain queued until prerequisites are reviewed. The primary does not edit files reserved for a worker concurrently. A dispatch tool call supplies title, brief, acceptance checks, optional dependencies, and committed base revision. Task IDs are plugin-generated, not predicted from Herdr labels.
3. The coordinator commits task intent before side effects, asks Herdr `worktree create --cwd <repo> --branch <task-branch> --base <base> --no-focus`, records returned worktree/workspace/root-pane IDs, then starts `omp` in that pane. OMP discovers the installed TypeScript extension both now and on Herdr resume; the extension uses the Herdr-provided pane identity to resolve its role, without an unsupported worktree-create environment flag. After confirming tool availability, the coordinator uses `agent prompt` to submit the brief. Each completed step is persisted so restart/retry can reconcile rather than repeat it blindly. The primary keeps the original checkout; workers start from a committed revision. Uncommitted primary changes are not copied implicitly. If a worker depends on them, the primary must ask for a checkpoint/decision before dispatching it.
4. Task creation does not steal focus. Herdr groups the worker workspace with the repository workspace. The coordinator verifies the exact recorded project and pane identity before prompt, focus, response, or cleanup.

`agent prompt` may time out after sending input. On timeout or `agent_prompt_stalled`, read the agent and task record before retrying; never resend merely because the call returned an error. If worktree creation or agent startup fails, keep an actionable failed task and the exact created resource IDs. Automatically remove only a positively identified, clean, unused worktree; never force-delete a dirty worktree or branch.

## Task facts, board stages, and supervision

Each task has an immutable ID, project key, brief, acceptance checks, base revision, branch, worktree/workspace identity, the worker process's launch-time `HERDR_PANE_ID`, the current public pane ID, dependency IDs, explicit worker reports, transition timestamps, error/attention facts, and durable notification delivery IDs. Persist the task lifecycle, not Herdr's transient agent status.

Board columns are **Queued**, **Running**, **Needs input**, **Ready for review**, and **Done**. Queued includes unprovisioned/dependency-gated tasks; Running includes provisioning and dispatched tasks; Needs input includes an explicit blocker, a crashed/absent worker, unknown runtime state requiring inspection, or recoverable dispatch failure; Ready for review requires a worker's explicit final report; Done requires the primary to record the user's review/integration disposition. The card also shows the current Herdr activity (`working`, `idle`, `blocked`, `done`, or `unknown`) as a separate indicator. `idle`/Herdr `done` never means task completion. A failed task remains visible rather than disappearing into Done.

The worker report contains result type, short summary, branch, changed-file or commit evidence, checks run and their outcomes, and any remaining risk. Reporting a result is not an automatic merge. The primary reviews it, summarizes actionable outcomes to the user and asks before integration. Marking a task Done records the disposition, but does not automatically remove the branch or worktree; cleanup is an explicit later action that refuses dirty worktrees.

Plugin event hooks handle Herdr agent-status changes for recorded worker panes and `pane.moved` updates to their current public pane IDs; a startup snapshot recovers missed moves. Status hooks write deduplicated observations/inbox entries and attempt to notify the primary when appropriate. A worker report also writes an inbox entry directly. When the primary is idle, notification can use `agent prompt` with a short task ID and event summary; when working, blocked, missing, or ambiguous, the event remains queued for the next safe primary turn. Notification IDs prevent duplicate messages after hook retries or restart. Event hooks must ignore status transitions of the primary caused by their own prompt. Plugin startup reconciles stored task identities with Herdr's live session/worktree snapshot; events are not treated as replayable history. Unknown/missing probes are attention signals, not proof that a worker failed or finished.

For an ordinary worker question, the primary asks the user and relays the answer to the same recorded worker. For a permission/choice dialog, `agent prompt` cannot address an already blocked agent; the primary must show the current dialog to the user, obtain explicit approval for a specific choice, re-read and verify that the same worker/dialog is still active, then send only the approved keys. Changed or unreadable dialogs require a fresh user decision. No blanket auto-approval.

## Recovery and safety invariants

- Reconcile from durable task facts plus exact Herdr IDs and Git worktree provenance, not from tab names or a remembered focus. A cross-workspace move changes the pane's public ID but leaves the live OMP process's launch-time `HERDR_PANE_ID` unchanged (Herdr retains it as an alias). Preserve that launch ID for bridge lookup; update **only** the current public ID for CLI calls and board focus using Herdr's authoritative move response or a verified session snapshot. If Herdr restarts the agent process, accept its new launch ID only after verifying the restored OMP session and pane/worktree binding; never re-key from a label or an unverified alias.
- A restart can restore OMP sessions through Herdr's installed integration. The plugin startup pass rebinds known tasks and the primary, rechecks pending dispatch steps, and queues unreported blockers/exits without respawning unknown occupants.
- Task updates and notification claims are transactional and idempotent. Event hook failures are logged and later reconciliation can recover observations; no event alone declares a task successfully delivered or completed.
- A primary loss does not destroy workers. The board marks its absence and retains inbox events. Re-establishing the primary requires an explicit launch/reattach action.
- All actions are local-user operations; the plugin is trusted code with Herdr and Git access. No public listener, background credential store, auto-push, auto-merge, or forced worktree removal is added.

## Validation plan

Unit tests cover legal task transitions, the distinct task-stage/agent-activity projection, concurrency cap/dependencies, inbox deduplication, idempotent partial dispatch, refusal to send to stale/mismatched identities, and a cross-workspace pane move that preserves bridge lookup by launch ID while updating the public ID used for CLI calls. Integration tests exercise Herdr CLI response parsing and failure cases through controlled fixtures. On Windows, a disposable OMP extension smoke test verifies tool registration, role gating, and coexistence with Herdr's OMP state extension; a restore test verifies that the orchestration tools are still available after `omp --resume=<session>` without `--extension`. The end-to-end acceptance run uses a disposable Git repository and installed Herdr+OMP integration to launch the primary, dispatch two workers, route one blocker through the primary, collect two reports, inspect the board, restart/reconnect Herdr, and confirm both task bindings and worktrees persist. Include a dirty-worktree cleanup refusal and a timed-out prompt inspection case. Do not test on the user's AO checkout or real project data.

- Herdr documents native worktree create/remove semantics and exact IDs: https://herdr.dev/docs/cli-reference/#worktrees
- Herdr documents cross-workspace pane moves and the process's retained launch-time `HERDR_PANE_ID` alias: https://herdr.dev/docs/cli-reference/#panes
- Herdr documents plugin panes, startup hooks, event hooks, and plugin-owned state dirs: https://herdr.dev/docs/plugins/
- Herdr documents non-replayed event subscriptions and snapshot reconciliation, including `pane.agent_status_changed`: https://herdr.dev/docs/socket-api/#event-subscriptions
- Herdr documents OMP integration lifecycle authority and session restore: https://herdr.dev/docs/integrations/#omp
- AO's current design distinguishes durable session facts from derived board status: `agent-orchestrator/backend/pkg/contract/kanban.go`, `agent-orchestrator/backend/internal/domain/activity.go` (reference only).
- OMP 18.3.1's installed `--help` supports `--extension` and auto-discovery (`--no-extensions` disables discovery); Firstmate's OMP extension registers `fm_watch_arm_omp` with `registerTool`, while AO's OMP adapter passes `--extension` on **both** launch and its own restore path. Herdr's documented `omp --resume=<session>` path does not promise that flag, so this plugin uses auto-discovery instead: https://github.com/kunchenguid/firstmate/blob/main/.omp/extensions/fm-primary-omp-watch.ts and `agent-orchestrator/backend/internal/adapters/agent/omp/omp.go` (reference only).

Before implementation, verify on the installed Windows Herdr/OMP versions: whether plugin event hooks accept `pane.agent_status_changed`, the exact OMP `registerTool` signature, effective user extension directory and discovery on both fresh launch and Herdr's `omp --resume=<session>` restore, Windows argv/console behavior for the Go executable and `agent start`, board-pane focus behavior, and the minimum Herdr version. An explicit-flag-only extension must **not** be accepted until a real restore proves Herdr preserves that flag. If a documented surface differs, preserve the user-visible contract with a bounded CLI/snapshot reconciliation fallback rather than inventing an unverified internal API.

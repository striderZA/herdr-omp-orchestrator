# Product intent and contract

This document is the tracked, contributor-facing statement of what the plugin is for and which boundaries must remain true. For implementation conventions and commands, see [AGENTS.md](../AGENTS.md).

## Goal and boundary

Make parallel coding in one Git repository feel like talking to one OMP agent instead of managing terminal tabs. A human works through one primary OMP session. The primary delegates independent, bounded tasks to workers; the plugin records task facts, reports, and inbox notes; and the human decides what to accept. Herdr remains the owner of the terminal and agent runtime. The plugin coordinates it; it does not replace it.

The supported product is a local, Windows-only Herdr plugin for one bound repository/project at a time. Its durable state lives under Herdr's plugin state directory, not in the project checkout or the installed extension. The task board is a terminal view, not a separate web or desktop product.

The founding design draft was removed in commit `82e84ef`; its source remains in Git history (`git show 82e84ef^:docs/superpowers/specs/2026-09-25-herdr-omp-orchestrator-design.md`). This document restates the current contract rather than copying that earlier draft verbatim.

## Scope

### In scope

- Bind a Git repository to a primary OMP session and record its verified Herdr identities.
- Dispatch independent work to isolated Herdr-managed worktrees and OMP worker sessions, subject to the coordinator's concurrency limit (three workers by default).
- Record worker progress, questions, blockers, and final reports durably; deliver notes to the primary without treating delivery or terminal activity as task completion.
- Let the primary review a final report and record an explicit outcome. Reconcile persisted facts with Herdr's live snapshot and worktrees after missed events or restarts.
- Provide a terminal board for task stages, details, and focusing a verified worker pane.
- Keep durable project tickets in `backlog` or `todo`. The board creates tickets and moves backlog tickets only through `TicketOps`; the coordinator atomically records a linked planner task on a move and starts or queues it. Later ticket stages derive from linked tasks and the ticket's recorded decision.

### Out of scope

- Multiple repositories under one ticket, remote workers, other agent harnesses, GitHub PR/CI/review automation, automatic merge or push, agent-to-agent hierarchy, mobile/browser UI, or a standalone network daemon.
- Treating Herdr's `idle`/`done` activity as evidence that work is complete. A task needs a final report and an explicit disposition.
- Automatic implementation dispatch from a plan. The primary reviews the planner's ordinary final report, obtains the user's acceptance, then explicitly dispatches implementation tasks.

## Success run

A successful first task run starts a primary in a repository, asks it for two independent changes, and observes two isolated OMP workers and task cards. The primary handles a worker's question or a specifically approved blocked dialog. The workers return reports with evidence and check outcomes; the user reviews the results, sees the branches, and records dispositions. After detaching/reconnecting or restarting Herdr, the same task facts and board state are recovered without silently adopting an unknown agent or resending an input whose outcome is uncertain.

The ticket path is additive: create a backlog ticket, confirm a move to `todo`, and the coordinator atomically records and starts or queues one planner task. Its final report is the plan; the existing task review records whether it is accepted. Plan approval never auto-dispatches implementation: the primary dispatches explicitly after the human checkpoint. After implementation tasks close, the user makes a separate ticket decision. A ticket does not become done just because its tasks or agents stop running.

## Ownership model

| Owner | Responsibility |
| --- | --- |
| **Herdr** | Persistent terminal processes, panes and workspaces, native worktree operations, focus, OMP agent lifecycle/session restore, and the plugin runtime environment. The plugin uses Herdr's CLI as the boundary for these operations. |
| **Plugin core (Go)** | The executable and routes, setup/bind/dispatch/review/cleanup policy, event observation and startup reconciliation, bridge authorization, durable project/task/ticket/inbox facts, and board projection. `internal/state` is the only persistence writer; `internal/coord` owns orchestration policy. |
| **OMP extension (TypeScript)** | The role-specific primary and worker tools and confirmation interactions. `omp/herdr-orchestrator.ts` is canonical; it sends the versioned, bounded bridge protocol to the Go executable. Setup installs this plugin's extension alongside, and never over, Herdr's OMP integration. |
| **Board** | Projects stored facts into a terminal view. It is read-only for tasks: it never writes or dispatches them directly. Its only ticket writes are create and backlog-to-todo through `TicketOps`, backed by the coordinator; a move records the planner task there. It may focus a verified worker pane, but does not call Herdr to write a ticket. |

## Safety invariants

1. **Facts before projections.** Persist task/ticket facts and explicit decisions. Derive stages from those facts. Agent activity, an idle session, and a closed pane do not complete work or a ticket.
2. **Identity from recorded facts.** Resolve project, task, and pane from the verified caller binding and persisted records, not caller-supplied IDs or labels. A bridge caller identity is attribution within one user account, not a defense against another process running as that same user; do not add a local secret that cannot protect this boundary.
3. **Fail closed on live identity.** Every bridge method routed through `mutate`—including previews and listings as well as writes—runs the role/readiness checks and the shared coordinator `agent get` confirmation; `resolve` and `ready` remain handshake methods. Refuse missing or contradictory agent/session/checkout/workspace evidence. Do not copy this check into individual operations.
4. **User confirmation for consequential actions.** Keep input injection, approval, primary replacement, and destructive cleanup behind their explicit user-confirmed paths; a stale plan/dialog or unknown identity must not be acted on. The only input-injection path without a preceding user-authorized operation is automatic inbox-note delivery to a primary positively verified as the recorded pane, agent kind, session, and project checkout, and `idle` at a fresh probe. This is point-in-time evidence, not a lock; `idle` does not prove the input line is empty, and draft behavior remains unverified. Notes are labeled worker/orchestrator-originated; that is provenance, not sanitization or user consent, approval, or answer. Actions on the consent list retain their dialogs. A worker brief may be submitted later by a queue drain, startup reconciliation, or recovery without a new dialog only as a continuation of a persisted dispatch intent previously admitted by the ticketless-request dialog, a user-confirmed ticket move, or accepted-plan plus primary dispatch; that is not a new authorization. An ambiguous input-delivery result is not permission to blindly send it again.
5. **No silent replacement or forced deletion.** Reattaching a lost primary is explicit. Reconcile known facts; never respawn or adopt an unknown occupant. Remove only a positively identified, clean, unused checkout, without force-removing it or deleting its branch.
6. **One writer and narrow board authority.** Write durable facts only through `internal/state`. The board's ticket operations stay behind `TicketOps`; the board never gains a task write or dispatch path.
7. **Ticket planning is durable and explicit.** The move and planner intent commit atomically before the coordinator starts or queues the ordinary worker. Planner briefs are bounded for Windows command-line encoding; oversized ticket text is refused before it is stored. Primary and planner sessions receive only read-only OMP tools plus their role-specific orchestrator tools, and keep that restriction for the life of the process; only implementation workers retain coding tools. Unlinked dispatch requires user confirmation of the exact request. Linked implementation dispatch needs at least one linked planner, and every linked planner must have an accepting disposition: a ticket with no planner or an unaccepted plan takes no linked work, and accepting a plan does not dispatch work automatically. Reconciliation notes a pre-existing todo ticket with no planner and never starts one silently.

### AgentPrompt and key-injection inventory

The four production `Herdr.AgentPrompt` calls and one `Herdr.AgentSendKeys` call in `internal/coord` have distinct, action-specific gates. The confirmation gates live in the OMP extension or the reattach route, not in `internal/coord` alone.

- **Dispatch brief (`dispatch.go`).** The OMP extension confirms the exact request for a new ticketless `orch_dispatch`. A new ticket-linked implementation dispatch has no new dialog: the primary invokes it after the user accepts a planner, and the coordinator/store require an accepted planner. A planner is created by the user-confirmed ticket move. Any authorized intent may queue; `DrainQueued`, startup `Reconcile`/`ResumeDispatch`, and background recovery can later reach `submitBrief` without a new dialog, continuing that persisted intent rather than creating a new dispatch. If a submission is ambiguous, `orch_adjudicate_dispatch` shows the inspected pane/digest and the coordinator rechecks it; only a user-confirmed `not_delivered` retries the brief, while `delivered` records it without another prompt.
- **Reattach notice (`reattach.go`).** The reattach pane shows the re-derived plan and asks the user to confirm it before calling `Reattach`; the notice itself has no separate dialog. A sent or uncertain notice is not resent on a retry of that same recorded replacement binding. A newly recorded replacement binding has its own notice attempt.
- **Inbox note (`reconcile.go`).** This is the only path without a preceding user-authorized operation; no user confirmation is required for the notification itself. The coordinator may attempt delivery after note writes whose ordinary path calls `flushAfterNote` (including worker notes and new task-attention notes), on primary-idle events, or during startup reconciliation. Background recovery suppresses note-triggered flushes. `FlushInbox` requires a fresh probe proving the recorded pane resolves to itself, runs the required agent kind, reports the recorded session, works in the project's checkout, and is `idle`. The check is point-in-time, not a lock. Notes are claimed before prompting; a prompt success is settled as `delivered` when that write succeeds, a coordinator-classified definite refusal returns them to `pending`, and an ambiguous or unreadable result is `uncertain`, never resent. A claim interrupted before settlement is recovered as uncertain on startup. The primary can inspect the delivery detail; reading the inbox does not settle it. The origin label does not sanitize worker-written text or make it user consent. `idle` does not prove the input line is empty, and the effect of a prompt on a partly typed draft remains unverified. `TestInboxDeliveryIsClaimedOnceAndNeverBlindlyResent` and `TestFlushInboxKeepsNotesPendingWhenPrimaryCheckoutIsUnreported` cover the no-resend and checkout gates.
- **Answer (`report.go`).** The OMP extension confirms the exact answer text before calling the bridge; the coordinator records the attempt before sending. If sending is ambiguous, `orch_settle_input` requires a user-confirmed decision; `not_delivered` clears that attempt, but a retry still requires a separately confirmed `orch_answer` with the exact text.
- **Approved dialog keys (`report.go`).** The OMP extension confirms exact keys for the previewed dialog; the coordinator re-reads the dialog and checks its digest before recording an attempt and calling `AgentSendKeys`. An ambiguous send blocks resending keys to the same still-visible dialog until the user confirms `orch_settle_input`; a newly previewed, different dialog can be handled only through a new exact-key confirmation. If a later check finds the worker no longer blocked, the coordinator may clear the stale attempt and send nothing.

This inventory does not change the explicit confirmation list in [AGENTS.md](../AGENTS.md).

## Ticket design decisions

These are the accepted Phase 1 and Phase 2 decisions for [issue #9](https://github.com/striderZA/herdr-omp-orchestrator/issues/9), recorded here because drafts under `docs/superpowers/` are not a reliable tracked reference in a normal checkout:

- A ticket is a durable fact that can exist before a task. Its stored columns are only `backlog` and `todo`; later stages derive from linked tasks and the ticket's own decision. A planner task is identified by the additive `Task.Role == "plan"`; the ticket stores no task list.
- A human may create and move tickets on the board. A primary may create tickets; its move uses the extension preview-and-confirm interaction. Workers have no ticket authority. Ticket access is project-scoped.
- Ticket creation and backlog-to-todo movement refuse text whose serialized planner brief exceeds the Windows command-line budget, before storing the ticket or planner intent. A confirmed move to todo atomically stores a linked planner task intent, then uses the ordinary worker dispatch and recovery path. Planner tasks use the standard report/review/disposition lifecycle and project to `planning` or `plan_ready`.
- An accepting planner disposition (`integrated` or `kept`) permits later linked implementation dispatch. An open or non-accepting plan blocks it, and so does a ticket with no planner yet: the coordinator's pre-check and the store's claim transaction both refuse it. Approval never auto-dispatches implementation work; the primary dispatches only after the human checkpoint.
- An already-todo ticket with no planner is never dispatched by an upgrade or startup pass; reconciliation records one deduplicated inbox attention note instead.
- Ticket completion is a separate explicit review using the outcome set from [ADR 0001](adr/0001-disposition-contract.md), and is refused while a linked task is open. Completing the last linked task does not decide its ticket.
- A `superseded` decision names where the work went: a successor task for a task, or a successor ticket for a ticket, which is a reference only and moves no linked task. Recording it releases no dependent. A separate, user-confirmed re-point moves queued dependents of a superseded task to its successor, and only an accepting successor releases them (ADR 0005).
- No cross-project tickets. The move/intent transaction is one-shot, and existing content-fingerprint dispatch detection (ADR 0002 / issue #4) remains unchanged.
- The extension derives primary/planner tool permissions from the bridge's verified persisted role, not prompt text. Generic tasks with no `ticketId` remain available only after the user confirms the exact dispatch request.

For compatibility assumptions about Herdr's protocol, CLI answers, fixtures, and verification, start at [Herdr facts](herdr-facts.md). For the task outcome contract, see [ADR 0001](adr/0001-disposition-contract.md).

### Known gaps in automated proof

- **Standalone `omp --resume=<session>` without `--extension`: not directly exercised.** A static read of `tests/acceptance_windows.ps1` shows Herdr server restart/reconciliation and restored role-tool checks (`T4.1–T8.2`), but it does not run that OMP command as a standalone invocation without the flag. Do not claim that exact invocation is proven by the acceptance suite.
- **Non-Windows hosts: no automated proof and not a supported target.** The manifest is Windows-only; the current commands and stateful acceptance suite target Windows.
- **Human comprehension: not automatable.** Acceptance drives the same visible confirmation paths and checks their exact content (for example `K5.1–K5.3`, `TK1.3c` and `D1.1d`), but it cannot prove that a real user understood a prompt.

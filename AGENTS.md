# Repository Guidelines

## Project Overview

This is a Windows-only Herdr plugin that connects Oh My Pi (OMP) agents to a durable task orchestrator. The Go executable handles plugin actions, event/startup hooks, the interactive board (read-only for tasks; it creates and moves tickets through one narrow interface), and a versioned bridge used by the OMP TypeScript extension. Task progress is based on recorded reports and decisions—not terminal activity. Tickets (a backlog and a todo column) are durable facts that exist before any task; a ticket's stage is derived from the tasks linked to it and from the user's decision, never stored.

## Architecture & Data Flow

- `cmd/herdr-omp-orchestrator` is the single executable entry point. `herdr-plugin.toml` maps its subcommands to setup, bind, startup, event, board, reattach, and bridge routes. Herdr runs action commands without a terminal, so an action that needs the user's confirmation only opens a plugin pane (`open-board`, `open-reattach`) and the pane asks.
- `internal/bridge` validates the extension's versioned JSON stdin/stdout protocol and authorizes calls using inherited Herdr pane identity plus the OMP session identity. Keep bridge errors machine-readable and fail closed on unverified identity.
  - The coordinator's `agent get` confirmation runs on every call through `mutate` (previews, listings and unwired methods included) at one shared seam: `bridge.Ops.VerifyCaller`, wired by `CoordinatorOps` to `coord.Coordinator.VerifyCaller`. After the role and `Ready` checks and before the operation, it re-reads Herdr's live agent for the principal's recorded pane (the public pane, else the launch pane) and requires the recorded agent kind, a session reference the confirmed handshake proves is the recorded session, the recorded checkout as its cwd and the recorded workspace; a binding that records no checkout or workspace is refused. A mismatch, a vanished agent or a malformed answer is `agent_changed`; an unreachable Herdr is `herdr_unavailable`. It reads persisted facts only and writes nothing. `resolve` and `ready` are the handshake and stay outside it; an `Ops` with no `VerifyCaller` refuses every method. Do not copy the check into individual operations.
  - The primary's read-only views of its own project are the additive bridge methods `task_list` and `inbox_list` (tools `orch_task_list`, `orch_inbox_list`; protocol stays 1). They are `RolePrimary` only, run through the same `mutate` authorization, take the project from the verified principal, and write nothing: listing an inbox note never claims or settles it, so an `uncertain` note stays uncertain and its `deliveryDetail` is the primary-facing way to read why. Answers are bounded by a row limit (default 50, at most 200), a rune bound on each text field and a byte budget that accounts for JSON escaping, and a cut list says `truncated`. Open tasks and undelivered notes come first so the cut loses decided or delivered history before anything waiting.
  - Tool access follows the verified binding, never prompt text. `resolve` additively reports a bound worker's persisted `taskRole` (`plan` for a ticket's planner) and `branch` (protocol stays 1). The extension gives the primary and a planner a read-only session: of the tools already active they keep only `read`, `grep`, `find` and `glob` plus their own orchestrator tools, a `tool_call` guard blocks every other call even if OMP enables it again, and a later `resolve` never lifts the restriction for that process; implementation workers and unbound sessions keep their tools. An `orch_dispatch` that names no ticket starts only after the user confirms the exact request (a declined or unavailable confirmation sends nothing). One that names a ticket goes to the bridge unchanged, and the coordinator's pre-check and the store's claim transaction admit linked work only when the ticket has at least one planner and every linked planner has an accepting disposition (`ticket_plan_not_accepted`).
  - Each extension consent dialog (`uiGate`, behind every confirmed action: a ticketless dispatch, a review, a ticket move or decision, an answer, a worker dialog approval, an input settlement, a dispatch adjudication, a cleanup and a re-point) marks its pane blocked while it waits for the user. It publishes `herdr:blocked` `{active, label}` on OMP's shared extension event bus (`pi.events`), which Herdr's OMP integration reports as the pane's `blocked` status, and clears the mark when the dialog settles, whatever the answer and even when the dialog fails. Herdr documents that it refuses `agent prompt` to a blocked agent before typing anything, so once the mark reaches Herdr a prompt is refused instead of landing in the dialog, where its Enter would choose the highlighted Yes. The mark is not a lock: a prompt sent before it reaches Herdr, keys sent with `agent send-keys`, and the user's own typing still reach the dialog, and the dialog's exact text is still what a confirmation must match. A declined or unavailable confirmation still sends nothing. `checkConsentMarksPaneBlocked` in `omp/load-extension.check.ts` proves the mark, and acceptance `TK1.3c-blocked` observes Herdr reporting it live.
  - Trust boundary: the bridge's caller identity is an *attribution* boundary inside one user account, not a security boundary against it. `HERDR_ENV`, `HERDR_PANE_ID`, `HERDR_PLUGIN_STATE_DIR` and the announced OMP session are all supplied by the caller, and a same-user process can already read the store and drive any pane through Herdr's own CLI, so spoofing them grants no authority the account lacks. Do not add a local secret (it would be readable by the same user) or treat the bridge as defending against that attacker. Instead keep the blast radius bounded: every operation must derive its project, task and pane from persisted facts (a caller that names one in `params` changes nothing), keep the role check and the coordinator's `agent get` confirmation on every mutating call, and keep destructive or input-injecting steps behind explicit user confirmation. Only inbox-note delivery lacks a preceding user-authorized operation: `FlushInbox` requires the recorded pane to resolve to itself, the required agent kind, recorded session and project checkout to be positively verified, and `idle` at a fresh probe; this is point-in-time evidence, not a lock. It claims notes before prompting, settles a success as `delivered` when that write succeeds, returns coordinator-classified definite refusals to `pending`, and marks unknown outcomes `uncertain` rather than resending; an interrupted claim is recovered as uncertain on startup. Notes are labeled as worker/orchestrator-originated; that is provenance, not sanitization or user consent. Actions on the explicit consent list above retain their existing dialogs. A worker brief may be submitted later by a queue drain, startup reconciliation, or recovery without a new dialog only as a continuation of a persisted dispatch intent admitted by the ticketless-request dialog, user-confirmed ticket move, or accepted-plan plus primary dispatch; it is not a new dispatch or an additional confirmation exception. `idle` does not establish an empty input line, and the effect of `agent prompt` on a partly typed draft remains unverified.
- `internal/coord` implements orchestration: bind/dispatch/review/cleanup, event observation, inbox delivery, and startup reconciliation. Events are one-shot observations; startup re-derives live identity from Herdr's snapshot and worktrees. A primary that is absent or unproven is recorded on the project (`task.Project.PrimaryAttention`) by reconciliation and the paths that probe the primary, and cleared once the primary is verified live; the board only reads that fact and draws a marker, and recording it changes no task, stage or inbox note.
  - `Bind` verifies its prerequisites before it records or starts anything: `coord.Options.Preflight` (wired by the executable to the read-only `setup.Verify`) must prove Herdr's OMP integration and the plugin's own extension are present in the effective OMP profile, or `Bind` refuses with `coord.ErrNotReady` (answered with `setup`'s own `integration_missing` / `extension_missing` code and the remedy) before `CreateProject`, workspace creation, any pane lookup or agent start. The check runs for a re-bind of a recorded project too, since reopening can start the primary's agent. `setup.Verify` shares `checkIntegration` with `Install`, never writes, and does not judge whether the installed extension is current; the extension's runtime `ready` handshake remains the second check. A coordinator built without a `Preflight` refuses to bind (`ErrNotReady`) instead of skipping the check, so the gate cannot be bypassed by omission; no other operation consults it.
  - Project writes refuse to share a pane. `state.Store.CreateProject` refuses, inside its transaction, a launch or public pane that another project or any task records (`state.ErrPaneTaken`, deliberately not `ErrConflict`), and `UpdateProject` refuses moving a project onto one; a write that keeps the panes is never refused for it. Task writes still check only other tasks (`checkPaneFree`), not project panes. `Bind` does not adopt a named pane that any record claims (it creates a dedicated workspace instead), and a store refusal surfaces as `coord.ErrAlreadyBound` (`already_bound`). Databases written before this still open: a launch pane two projects record makes `ProjectByLaunchPane`/`ByPane` fail closed with `state.ErrAmbiguous`, and the bridge resolves it as `ambiguous_session` without adopting a session.
  - Reattaching a lost primary (`coord.PlanReattach` / `coord.Reattach`, routes `open-reattach` and `reattach`) is the one explicit, user-confirmed way to move a project to a replacement pane; `Bind` keeps refusing silent substitution and its refusals name the action. The plan is read-only and is what the user confirms; `Reattach` re-derives it and refuses unless it still matches, records the binding in one compare-and-swap of the project row (the displaced identities go to `task.Project.Replaced` in the same write), and then confirms the handshake with one notice to the replacement session plus `awaitAgentReady`. The write precedes the notice because the replacement's extension can only announce once the project records its session, so a failure afterwards is `ErrReattachPending` with the binding left recorded and marked in `PrimaryAttention` - never reported as success. The notice is an input injection, so its attempt (`task.Project.ReattachNotice`, with the pane, session and session-reference kind it went to) is persisted before the prompt is sent and follows the inbox rule across retries of that same recorded replacement binding: a notice Herdr acknowledged (`sent`) or whose outcome is unknown (`uncertain`: an ambiguous or unreadable answer, or a stopped process) is never sent again by a retry of that binding, which only waits for the handshake. A newly recorded replacement binding has its own notice attempt. Only a refusal that proves nothing was written withdraws the attempt. Identity checks fail closed: a recorded session and Herdr's reference are only compared in the same form (id or session file), so a recorded pane whose session is now reported in the other form is refused unless a verified handshake proves it is a different session; and the flow goes on to the notice only when the readiness store reports no announcement for the pane (`state.ErrNotFound`) or an earlier session's (`state.ErrMismatch`) - any other confirmation failure, including `ErrAgentChanged` after a recorded confirmation, sends nothing. If the session still has not announced, the user sends it a message and `bind` confirms it. Reattach never replaces a primary that is verified live and never adopts a pane or session that a worker or another project owns; running it again on a recorded replacement does not record the displaced primary twice.
- A ticket move and its planner intent commit in one store transaction; starting the planner is a later step. A move whose planner then fails to start is still a move: `MoveTicketFor` returns the moved ticket with `coord.PlannerNotStartedError` (`errors.Is` `ErrPlannerNotStarted`), the bridge answers `ticket_move` ok with the additive `plannerNotStarted` (protocol stays 1), and the executable hands the board a `board.MovedTicketError`, so the board says the ticket moved and why its planner has not started. A queued task's slot claim that outlived its caller (older than the step lease, no live step claim: `state.Store.SlotClaimAbandoned`) is continued by the next drain the way a deliberate resume continues it, step claim first; a fresh claim stays its caller's. Slot and step claims record their owning process identity; live or unverifiable owners are never taken over, while legacy rows without identity retain the lease-only fallback. Startup, bridge `dispatch`/`review`/`ticket_move`/`adjudicate_brief`, and board ticket moves arm a detached Windows recovery worker before the route runs; failure to launch or arm refuses before the operation. The worker waits for explicit route completion or parent exit, then runs identity-checked claim recovery over due claims only (`RecoverUntilIdle`, ADR 0004): it never reconciles a task with no claim, settles a cleanup, or delivers an inbox note, and it stops once no claim is left to attempt or await. Recovery is scoped to claims from the completed operation; board moves also filter to their ticket so later moves in the same process are not fenced. This is not a persistent service, and bind intents retain their separate explicit proof path ([#58](https://github.com/striderZA/herdr-omp-orchestrator/issues/58)).
- Successors and re-points (ADR 0005, issue #61): a `superseded` decision names a validated successor (a task for a task, a ticket for a ticket) through the single validation point `coord.checkSuccessor`, and the store repeats the same rules inside the decision's write transaction. Only a superseded decision may name one, a repeat is idempotent only with the same successor, and recording `superseded` releases no dependent. The primary's `repoint_preview` and `repoint` bridge methods (tool `orch_repoint`, both `RolePrimary` through `mutate`) rewrite only the named queued dependents of a superseded task to its successor. `state.Store.RepointDependents` checks the superseded task, the successor, each dependent's confirmed revision, that every dependent is queued with no provisioning slot, and that the project's dependencies stay acyclic, all inside one transaction that writes every dependent or none. A ticket successor is a reference and is never re-pointed.
- Recovery worker limits (ADR 0004): each due claim is paced on its own. A claim a pass declined waits its own backoff (1s to 30s, seven declines) and is then exhausted; the worker stops with `ErrRecoveryStalled` once no claim is left to attempt or await. An exhausted claim keeps its slot until startup, or a drain of a queued task, continues it. A worker never waits on a claim its own pass left: it fences the claims it attempted. A recorded step is continued only for a pane Herdr proves; otherwise it is declined, and the reason is recorded as the task's attention (not a blocker, and still recoverable). Background passes judge only due claims with no live owner, never a task with no claim or a blocked one, and never settle in-flight inbox deliveries (`RecoverInbox`), settle interrupted cleanups, or flush notes; only startup does those. Recovery admits no work over a held slot: it resumes a recorded step, and it continues a claimed queued task only through the same slot gate a dispatch passes.
- `internal/herdr` is the CLI boundary: execute argv directly (never through a shell), decode Herdr's JSON into typed values, and leave policy/state changes to the coordinator.
- `internal/state` is the only writer of durable orchestrator facts (tasks and tickets), stored in SQLite under Herdr's plugin state directory. `internal/task` defines those facts and derives the board stage (and a ticket's stage from its linked tasks). `internal/board` presents a view that is read-only for tasks: the human can create a ticket and move a backlog ticket to todo only through its injected `TicketOps`, which the executable backs with `internal/coord`; the board never writes a task, never dispatches, and never calls Herdr for a ticket write. `internal/setup` installs the extension without overwriting Herdr's integration.
- Data generally flows from plugin/extension input → `bridge` or CLI route → `coord` policy → `state` persistence, with the board projecting persisted facts back to the user (and, for tickets only, writing through `coord` via `TicketOps`). `omp/herdr-orchestrator.ts` is the canonical extension source; edit it here, then rerun setup to refresh the installed copy.

## Key Directories

- `cmd/herdr-omp-orchestrator/` — process routing and CLI tests.
- `internal/` — Go domain, persistence, CLI integration, orchestration, bridge, setup, and board packages; each package has adjacent `_test.go` files.
- `omp/` — canonical OMP extension and its schema/load check.
- `tests/` — Windows PowerShell helper-contract and full acceptance suites.

## Development Commands

Run from the repository root:

```sh
go test ./...
go build -o herdr-omp-orchestrator.exe ./cmd/herdr-omp-orchestrator
```

The plugin manifest builds without CGO; on Windows the equivalent is:

```powershell
$env:CGO_ENABLED = '0'
go build -o herdr-omp-orchestrator.exe ./cmd/herdr-omp-orchestrator
```

Windows acceptance checks:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\acceptance_helper_tests.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\acceptance_windows.ps1
```

The full acceptance test drives real Herdr and OMP sessions in an isolated named session and temporary worktree root; it supports `-TimeoutScale`, `-KeepResources`, `-SkipStateCleanup`, and `-Model`. `-Model` (default `openai-codex/gpt-6-luna`, spelled as `omp --model` spells it; `-Model ''` keeps OMP's own default) pins the primary and every worker to one model without touching the user's OMP settings: the run writes a one-file OMP config overlay into its temp root and names it in `PI_CONFIG_FILES` on the isolated Herdr server, whose agents inherit it. The run first checks that OMP resolves the overlay (`S1.2b`, fail-closed), then reads each session's transcript to assert every assistant turn used that model (`N7.4`, `SW0.1b`, `W2.<A|B>-model`). With a model pinned those checks fail closed: a session whose transcript cannot be read, or that ran any turn on another model, is a FAIL, not an INFO. With no model pinned they only record the model OMP chose. The extension load check can also be run with Bun and OMP's schema builder available: `bun run omp/load-extension.check.ts` (see `omp/load-extension.check.ts` for builder resolution options).

## Git Hooks

Enable the repository hooks once per clone:

```sh
git config core.hooksPath .githooks
```

The hooks require Conventional Commit subjects (`<type>(optional-scope): <short description>`) and reject staged files under `docs/superpowers/` or `.superpowers/`.

## Releasing

The plugin version is `version` in `herdr-plugin.toml`, in semver. Cut a release from the default branch: merge the version bump, tag that commit `vX.Y.Z`, and make sure its manifest declares `X.Y.Z`.

1. Merge the version bump to the default branch.
2. Tag the merged commit and push the tag: `git tag -a vX.Y.Z -m "vX.Y.Z"`, then `git push origin vX.Y.Z`.
3. Publish the release: `gh release create vX.Y.Z --verify-tag --generate-notes`.

`.github/workflows/release.yml` then builds `herdr-omp-orchestrator-windows-amd64.exe` with `-X main.version=X.Y.Z`. It fails unless the tagged manifest declares that version and the binary reports it (`herdr-omp-orchestrator --version`), and it attaches the binary and `SHA256SUMS` to the release. Local builds report `dev`. The workflow does not run the tests, so run `go test ./...` on the commit before tagging. To rebuild an existing release's assets, run the workflow by hand with the tag.

## Code Conventions & Common Patterns

- Use standard Go formatting and idioms; keep package responsibilities and existing boundaries intact. Test files use Go's `testing` package and are named beside the implementation as `*_test.go`.
- Pass `context.Context` through external operations and bound subprocess/protocol calls. Herdr commands use `exec` with argv, not shell strings; enforce input/output limits where the protocol defines them.
- Compare stable errors by code or with `errors.Is`/`errors.As`, not by matching prose. Preserve the bridge's JSON envelope and protocol version when changing either side of the Go/TypeScript seam.
- Treat durable records as facts and derived views as projections. Do not infer task completion from Herdr's idle/done activity; a final report and explicit disposition drive the task lifecycle. Event hooks apply one observation; reconciliation handles missed events/restarts.
- A final report's checks are `task.Check` values that each state an outcome (`passed`, `failed` or `skipped`); `coord.validateReport` is the one place that requires it (ADR 0003). A report stored with free-text checks decodes to checks with no outcome and is rendered as recorded: never invent an outcome for one. Change the extension schema, the worker instructions and the Go validation together.
- Keep `internal/state` as the persistence writer. Inject narrow client interfaces where a package needs Herdr behavior, and maintain fail-closed identity checks and explicit user confirmation for input injection or destructive cleanup.
- TypeScript schemas must use factory defaults for mutable values (for example, `.default(() => [])`), not shared mutable defaults.

- `cmd/herdr-omp-orchestrator/main.go` — subcommand routing and route-level bounds.
- `internal/bridge/bridge.go` — extension protocol and caller authorization.
- `internal/coord/` — task lifecycle and reconciliation behavior.
- `internal/state/sqlite.go` / `internal/task/model.go` — durable schema and domain projections.
- `omp/herdr-orchestrator.ts` — canonical OMP extension source; `omp/load-extension.check.ts` validates it against OMP's actual schema builder.

## Runtime/Tooling Preferences

- Primary runtime/toolchain: Go 1.27.1. Dependencies are managed by Go modules (`go.mod`, `go.sum`); there is no Node package manifest or separate Go lint/formatter config in the repository.
- Target platform is Windows (`herdr-plugin.toml`); the SQLite driver is pure Go, and the plugin build uses `CGO_ENABLED=0`.
- Bun is needed only for the TypeScript extension load check. That check also needs OMP's schema builder available locally; the corresponding Go test skips when Bun or the builder is missing.
- PowerShell 5.1 or newer runs the acceptance scripts. Avoid editing Herdr's installed integration or the installed extension copy directly; setup owns installation of the extension source.

## Testing & QA

- `go test ./...` runs package-level tests. Tests use temporary SQLite databases, fixture data, and—in coordinator tests—a real temporary Git repository plus a child process acting as a Herdr CLI stand-in, so retry and argv behavior are exercised at the boundary.
- `tests/acceptance_helper_tests.ps1` tests pure helper contracts without Herdr, an OMP session, or network access. `tests/acceptance_windows.ps1` is the stateful end-to-end acceptance path and cleans up only resources it created unless explicitly told to keep them. As the user, it confirms only the exact dialog a step requested. It types a prompt into the primary only once Herdr reports the primary idle or done, never into a blocked or busy one; where a step first resolves the primary's pending input (`Resolve-PendingPrimaryDispositionAsks`, which also guards Phase 18's deliberately ambiguous prompt: `G0.settled`), any extension consent dialog no step asked for is declined with Escape, never Enter. A primary that does not settle gets no prompt, and the refusal says why. After the restart it requires a proven live identity only of the tasks startup reconciles (`reconciles()`); a decided task is history (`T5.session/<id>` is INFO).
- Extension loading is verified with OMP's real schema builder via `omp/load-extension.check.ts`; the Go setup test invokes it when local prerequisites exist.
- When changing protocol behavior, lifecycle rules, or state migrations, update the affected package tests and preserve fail-closed behavior; run the focused package test(s) and the relevant helper/load/acceptance check for the changed behavior.
